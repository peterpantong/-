## 데이터 스키마 — 지금 것보다 나은 형태

제작방법 문서의 홀 구조가 현재 `build.py` 스키마보다 낫습니다. 데이터에는 이미 넣어
두었지만 **렌더러는 아직 쓰지 않습니다.** 다음 레이아웃 작업 때 이 필드를 쓰면 됩니다.

```jsonc
{
  "title":   "10m 내리막 · 오프닝",        // 홀 한 줄 성격. 머리말 옆에 붙임
  "marks": [                               // 체크포인트 — [라벨, 내용] 표
    ["우측 페어웨이 벙커 3개", "그린까지 205 · 181 · 168yd 남는 자리에 사선으로 놓임"],
    ["IP 지점", "BLACK 213 / BLUE 186 / WHITE 168 / RED 146yd — 남은 거리 140yd"]
  ],
  "play": {                                // 공략 3블록
    "tee":    "티샷 …",
    "second": "세컨드 …",
    "green":  "그린 …"
  },
  "caution": "오른쪽 벙커 사선만 피하면 파 확률이 가장 높은 홀",   // 강조 바 한 줄
  "tees":    { "black": 323, ... },        // 사이트 표기 미터
  "tees_yd": { "black": 353, ... }         // 원문 야드
}
```

현재 렌더러가 쓰는 필드: `par` `handicap` `tees` `green` `hazards` `bogey_plan`
`single_plan` `shape` `elevation`.
보관만 하는 필드: `title` `marks` `play` `caution` `tees_yd`.

### 왜 이 형태가 나은가

지금 제 홀 페이지는 `공략 포인트` 를 그냥 불릿으로 나열합니다. 참조본은
**체크포인트(숫자)** 와 **공략(문장)** 을 분리하고, 공략을 티샷/세컨드/그린 세 블록으로
고정했습니다. 라운드 중에 필요한 순서대로 읽힙니다.

## 참조본 홀 페이지 레이아웃 (22쪽 PDF 4쪽)

다음에 레이아웃을 다시 짤 때 이 구성을 따르면 됩니다.

```
[OUT] 1 [PAR 4] [HDCP 15]  10m 내리막 · 오프닝     ← 칩 + 큰 홀번호 + 한 줄 성격

┌────────────┐  ┌──────┬──────┬──────┬──────┐
│            │  │BLACK │BLUE  │WHITE │RED   │     ← 티 카드 4장 (색점 + yd 크게 + m 작게)
│  홀 도면    │  │353yd │329yd │308yd │286yd │
│  (실제      │  │323m  │301m  │281m  │261m  │
│   이미지)   │  └──────┴──────┴──────┴──────┘
│            │  체 크 포 인 트
│            │  ─────────────────────────────
│            │  우측 페어웨이 벙커 3개 │ 그린까지 205 · 181 …   ← marks 표
│            │  IP 지점              │ BLACK 213 / BLUE …
└────────────┘  공 략
 홀 레이아웃 ·   ┌────┬──────────────────────┐
 흰 숫자는…      │티샷│ 10m 내리막이라 …      │              ← play 3블록
                 ├────┼──────────────────────┤
                 │세컨│ 100yd 안쪽이 …        │
                 └────┴──────────────────────┘
                 ▌주의  오른쪽 벙커 사선만 피하면 …           ← caution 강조 바
                 [ 그린 확대 이미지 ]
                 SCORE □□□□  /  PUTT □□□□
```

A4 세로, 홀당 한 페이지. 왼쪽 도면 약 38%, 오른쪽 약 58%.

## 검증 방법 — 실제로 오류를 잡은 것들

숫자를 옮길 때 이 검산들이 값을 했습니다. 다음에도 그대로 쓰면 됩니다.

### 1. 캐리 박스는 그린까지 거리가 티와 무관해야 한다

도면에 티별 캐리 거리가 상자로 적혀 있으면, **같은 지점이므로 전장에서 빼면 네 티 모두
같은 값**이 나와야 합니다. 아난티 1번홀:

| | BLACK | BLUE | WHITE | RED |
|---|---|---|---|---|
| 전장 | 353 | 329 | 308 | 286 |
| 캐리 박스 | 271 | 244 | 223 | 201 |
| **차 = 그린까지** | **82** | **85** | **85** | **85** |

편차 3yd → 같은 지점이 맞습니다. 편차가 크면 그 숫자는 캐리 박스가 아니라 다른 것입니다.
이 성질로 **한 티 기준 거리에서 나머지 세 티 거리를 환산**할 수도 있습니다.

### 2. HDCP 는 1~18 이 한 번씩

전사 오류를 싸게 잡습니다. 아난티는 통과했습니다.

### 3. 홀별 합계 ↔ 스코어카드 합계 ↔ 공식 표기

아난티는 홀별 합이 **7,130yd**, 공식 소개는 **7,244yd** 였습니다.
어느 쪽을 쓸지 정하고 **문서에 차이를 적어 두는 것**이 정직합니다. 홀별 수치를 택했습니다.

### 4. 미터는 환산하지 말고 사이트 표기를 쓴다

3번홀 391yd 를 환산하면 357.5 → 358m 인데 사이트 표기는 **357m** 입니다.
표기값을 그대로 쓰고 원문 야드는 `tees_yd` 에 따로 보존했습니다.

### 5. 소스가 둘 이상이면 교차 대조

PDF 스코어카드 ↔ PDF 홀 페이지 ↔ MD 세 소스를 홀별로 대조해 par/hdcp/티 4개가 전부
일치하는 것을 확인했습니다.

## 함정

### 검색 요약을 근거로 쓰면 안 된다

"부곡CC 1번홀"을 검색하니 *"334m 파4, 우측 해저드 좌측 벙커"* 가 나왔습니다.
같은 문장을 **다른 골프장 이름으로 다시 검색하니 그 골프장 것으로 바뀌어** 나왔습니다.
요약기가 질문의 단어를 되돌려준 것이라 근거가 되지 않습니다.

**검증법**: 같은 내용을 다른 코스 이름으로 재질의해 보고, 따라오면 버립니다.

파72 라는 검색 결과도 틀렸습니다. 실제는 **파 73** (OUT 37 + IN 36).

### 공략을 지어내면 안 된다

"3번 홀은 오른쪽에 벙커가 있으니 주의" 같은 문장은 어느 코스에나 붙습니다.
**도면에 인쇄된 수치를 근거로만** 씁니다. 참조본의 좋은 예:

> 위험은 오른쪽 벙커 사선 하나뿐 — BLACK 기준 150~185yd 구간에 세 개가 겹쳐 있으니
> 페어웨이 왼쪽 절반만 보고 친다.

`150~185yd` 가 도면에서 나온 숫자입니다.

### 도면이 없는 골프장이면 만들지 않는다

홀별 야디지 표만 있으면 스코어카드와 거리까지는 됩니다. 벙커 위치·그린 컨투어는
**없으면 비워 두는 것**이 맞습니다.

## 이 작업 환경(클라우드 세션)의 제약

| 경로 | 결과 |
|---|---|
| `ananti.kr`, `cdn.ananti.kr` | CONNECT 403 — 이그레스 정책 차단 |
| `bkcc.co.kr`, `cdn.playwright.dev` | 같은 403 |
| 헤드리스 브라우저·플러그인 | 같은 프록시를 타므로 동일하게 차단 |
| 대화에 붙여넣은 스크린샷 | 눈으로는 읽히지만 **파일로 저장 불가** |
| **파일 업로드** | `/root/.claude/uploads/<세션>/` 에 **들어옴** ← 이번에 이걸로 풀렸음 |

정리하면 **클라우드 세션에서는 파일 업로드가 유일하게 되는 반입 경로**입니다.
직접 내려받아야 하면 환경의 Network access 를 `Custom` 으로 바꿔 도메인을 허용하고
**새 세션**을 시작하거나, 로컬 CLI 에서 받아 저장소에 푸시해야 합니다.

### 스크린샷도 데이터로는 쓸 수 있다

파일로는 못 받아도 **읽어서 숫자를 옮길 수는 있습니다.** 1번홀은 스크린샷 한 장으로
par/HDCP/티거리/캐리박스/설명문을 전부 채웠고, 나중에 원본 PDF 와 대조해 정확히
일치했습니다. 그림 자체를 PDF 에 넣을 때만 파일이 필요합니다.

## 만들어 둔 도구

| 도구 | 용도 |
|---|---|
| `tools/fetch_images.py` | URL 패턴(`…hole{hole}.jpg`)으로 18홀 도면 일괄 내려받기. 내용으로 확장자 판별, 404 를 200 HTML 로 주는 사이트 거름 |

`fetch_images.py` 가 못 쓰이지만, 로컬에서는 그대로 됩니다.

## 다음에 다른 골프장으로 만들 때

1. 공식 코스 페이지를 찾습니다 (예약 대행 사이트 말고 골프장 홈페이지)
2. 홀 이미지가 **사진인지 야디지 도면인지 실제로 열어서** 확인합니다.
   도면이면 벙커 잔여거리·IP 티별 거리·100/150야드 라인이 인쇄돼 있습니다
3. 도면과 홀 데이터를 받아 `data/<코스>.json` 에 채웁니다
   (`title` `marks` `play` `caution` 까지 채우면 다음 레이아웃에서 바로 쓰입니다)
4. 위 **검증 5가지**를 돌립니다
5. 이미지는 `images/<prefix>_holeNN.jpg` 규칙으로 넣고 `course.image_prefix` 를 지정합니다
6. `python build.py --data data/<코스>.json` 로 뽑습니다

바꿔야 하는 건 **데이터 파일 하나**입니다. 코스에 종속된 문구는 코드에 없습니다.

## 아직 안 한 것

- 홀 페이지 레이아웃을 위 참조본 형태로 다시 짜기 (`title`/`marks`/`play`/`caution` 사용)
- 참조 PDF 안의 실제 코스 도면 이미지 추출 → `images/` 에 넣기
  (`pypdf` 가 이 환경에서 `_cffi_backend` 오류로 멈췄음. `pypdfium2` 나 `mutool` 로 재시도)
- 부곡CC 데이터 (아직 par/거리 전부 비어 있음)
